# Milestone: config home + universal variables

Design ref: docs/DESIGN.md "After the PoC" item 4. Predecessors: PoC,
UX, funcs, lang milestones, all complete at 6d24c97.

## Goal

fush starts up like a real shell: reads the user's config, restores
variables that survive restarts, and has the `true`/`false` builtins
that the Windows smoke exposed as missing.

```
%USERPROFILE%\.config\fush\config.fish     ; sourced at startup (TTY and -c)
set -U greeting hello                       ; survives restart
fush -c 'echo $greeting'                   ; hello (loaded from disk)
true; and echo yes                          ; yes (builtins now)
```

## Task 1 — true/false builtins + config dir plumbing

Extend src/builtins.rs, src/repl.rs (or a new src/config.rs):

- `true` / `false` builtins: zero args (error on args), status 0/1, no
  output. Add to BUILTIN_NAMES so highlighting colors them.
- New module src/config.rs: `config_dir()` — %USERPROFILE%\\.config\\fush
  on Windows, $HOME/.config/fush on Unix (reuse the home_dir logic
  pattern from src/repl.rs history_dir_for; keep it testable via
  injected home/userprofile like history_dir_for is). `config_path()` =
  config_dir()/config.fish.
- History stays where it is (Windows %USERPROFILE%\\.fush — do NOT move
  it; note in report if you think it should move to .config\\fush
  later, with reasons, but don't change it).
- Tests: builtin true/false status, BUILTIN_NAMES contains them,
  config_dir_for both platforms, config_path join. cargo test green,
  clippy clean. Commit: `config: true/false builtins; config dir plumbing`

## Task 2 — config.fish sourcing

Extend src/main.rs / src/repl.rs / src/exec.rs as fits:

- At startup, before the first prompt / before running -c or a script:
  if config_path() exists, parse + run it in the Runtime (same execution
  path as -c, sharing the Runtime instance — config runs ONCE, errors
  print as `fush: config: <msg>` to stderr and DON'T abort the shell)
- Runs in ALL modes (TTY, -c, script file) — a var set in config.fish
  must be visible to `fush -c 'echo $greeting'`
- Config runs with cwd unchanged; `set -l` at config top level does
  what set -l at top level does today (documented, not changed)
- Tests: config file with set/abbr/function definitions → var visible,
  function callable, abbr expanded in TTY loop (unit-test the abbr
  table handoff if the TTY loop isn't reachable from tests; integration
  test the -c path end-to-end with a temp config dir via injected
  config path), config with a parse error → shell continues, config
  with a failing command → shell continues. Commit: `config: source config.fish at startup`

## Task 3 — universal variables

Extend src/builtins.rs, src/runtime.rs, new src/universal.rs:

- `set -U name values...` — stores in the global env AND persists to
  config_dir()/universals (format: simple `name<TAB>value1<TAB>value2`
  lines, one per var; document the format in the report; multi-line
  values are out of scope — reject with a clear error)
- At startup, after config.fish: load universals from disk into the
  global env (before config runs? AFTER config — config can override a
  universal for the session; document the order chosen: config first,
  then universals load, then... actually fish loads universals before
  config. PROBE real fish: `fish -c 'set -U x 1; echo $x'` then new
  fish `echo $x` — and check whether config.fish sees universals in
  fish (it does). So: universals load FIRST, then config. Document.)
- `set -U` on an existing universal updates it; `set -e` erases both
  env and file (check what set -e does today — extend to universal
  erasure if the file exists)
- `set -Ul` (local universal) is REJECTED with a clear error (fish
  allows it; out of scope)
- Startup load failure (corrupt file): skip bad lines, print one
  warning, continue
- Tests: set -U round-trip (set, new Runtime, load, assert), erase,
  multi-value, tab-in-value rejection, corrupt-line skip, universals
  visible to config.fish (integration with injected paths), -c mode
  sees universals. Commit: `config: universal variables with disk persistence`
