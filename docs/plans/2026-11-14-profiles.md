# Profiles milestone

Goal: named allow-list shells per docs/DESIGN.md "Profiles (agent allow-lists)".
Start fush with `--profile NAME`; the session permits only what the profile
allows. Fail closed with a clear message and non-zero status. `--profile`
without a name = read-only shell (no externals at all).

## Non-goals

- No per-argument allow rules beyond a fixed-argv form (skip prefix rules this
  milestone; a later one can add them)
- No `profile` builtin beyond `allow`/`deny` used inside profile files
- No profile switching mid-session
- No UI to create profiles (files are hand-written)

## Design decisions

- Profile state lives in `Runtime` (like functions/abbrs): a
  `profile: Option<Profile>` where `Profile` holds the collected allow-list.
- The gate is at the TWO process-spawn/file-write points, not at parse time:
  - `run_pipeline` external arm (src/exec.rs): before spawning an external,
    check the command name against the allow-list
  - `apply_redirects` + `emit_builtin_output` (src/exec.rs): before opening
    any redirect target for writing, check the path against the write-list
  - Command substitution inherits the check for free: it runs through
    `run_pipeline`/`capture_stmts`, which hit the same gates
- Builtins and functions run freely (the language itself is safe); `cd`
  stays free (directory change is not a process spawn or file write)
- Allow-list semantics: EMPTY allow-list = allow NOTHING (fail closed), not
  allow-everything. A profile file that never calls `profile allow` permits
  no externals — same as `--profile` with no name.
- Profile files: fish-syntax, sourced at startup BEFORE config.fush (a
  profile constrains the session; config customizes it). Location:
  `<config_dir>/profiles/NAME.fush`. Missing profile file with an explicit
  `--profile NAME` = hard error at startup (fail closed), exit 2.
- `profile` builtin (valid only while loading a profile file; error
  otherwise):
  - `profile allow CMD...` — add command names (exact match; PATH lookup
    resolves the same name the gate sees)
  - `profile allow-write PATH...` — add write-allowed paths; matching is
    path-prefix (component-wise: `C:\work` allows `C:\work\*`), absolute
    paths only; relative targets are rejected at the gate unless the
    resolved absolute path is under a listed prefix
- Gate messages: `fush: not allowed in this profile: <cmd>` (stderr,
  status 1) and `fush: not allowed in this profile: write to <path>`
  (status 1). Both leave $status set to 1 and continue (fish semantics:
  a failed command does not kill the shell).

## Tasks

### Task 1: `--profile` flag + Profile state + `profile` builtin

- src/main.rs: parse `--profile [NAME]` (NAME optional; next arg that is
  not a flag is the name — but only if it does not look like a flag; a
  script path after `--profile` is ambiguous, so `--profile NAME` consumes
  exactly one argument; `--profile` alone = read-only). `--profile` with
  no NAME and no further args = read-only interactive shell. Reject
  `--profile` twice (error, exit 2). Update `-h`/`--help` text.
- src/runtime.rs: `pub struct Profile { pub allow: BTreeSet<String>, pub
  allow_write: BTreeSet<String> }`; `Runtime.profile: Option<Profile>`;
  `Runtime.profile_loading: bool` (true only while sourcing the profile
  file). Methods: `Runtime::profile_allows(&self, cmd: &str) -> bool`,
  `Runtime::profile_allows_write(&self, path: &Path) -> bool` (component-
  wise prefix match, case-insensitive on Windows via eq_ignore_ascii_case
  on components, absolute-only).
- src/builtins.rs: `profile` builtin. Args after `profile`:
  `allow NAMES...` / `allow-write PATHS...`. Any other form: usage error
  `profile: expected 'allow CMD...' or 'allow-write PATH...'` exit 1.
  When `rt.profile_loading` is false: `profile: only valid while loading
  a profile` exit 1. When `rt.profile` is None (read-only mode): the
  builtin still records into a scratch list that is then DISCARDED —
  simpler: read-only mode sets `profile: Some(Profile::default())` with
  loading=true during a virtual load, so the same code path works; after
  load, loading=false. Prefer whichever is less code.
- src/profile.rs (new): `pub fn load_profile(rt: &mut Runtime, name:
  Option<&str>) -> Result<(), String>` — resolves `<config_dir>/profiles/
  NAME.fush` (None = read-only, no file), sources it with
  `profile_loading=true`, errors bubble as `fush: profile: <msg>` exit 2
  at startup.
- Wire into main.rs before config: interactive AND -c AND script modes all
  honor `--profile` (the flag is global, not REPL-only).
- Unit tests: flag parsing (name/no-name/twice), builtin allow/allow-write
  accumulation, usage errors, profile_allows + profile_allows_write matrix
  (prefix component match, case on Windows, relative-path rejection).
- Commit: `profiles: --profile flag, state, and profile builtin`

### Task 2: gates at spawn + redirect

- src/exec.rs external arm in `run_pipeline`: before building the child
  command, `if !rt.profile_allows(&name)` → eprintln the not-allowed
  message, set status 1, continue pipeline loop with `status = 1` (same
  shape as a failed external: next stage sees status; last stage's
  status is the pipeline's).
- src/exec.rs `apply_redirects`: for `(Out, _)` and `(In, 0)` redirect
  targets, resolve to absolute (std::fs::canonicalize on the parent of
  the target if the file doesn't exist yet; fall back to current_dir join)
  and check `rt.profile_allows_write`. Not allowed → same message shape,
  Err from apply_redirects (existing error path already prints and sets
  status 1).
- src/exec.rs `emit_builtin_output`: same check before `File::create`.
- Note: `cd` builtin and function calls are NOT gated (per design).
  `test`, `echo`, etc. run free. The ONLY gates: external spawn, write
  redirects (external and builtin), input redirects (reading a file is
  also gated? DESIGN says file writes are the danger; reading is not
  listed. Gate writes only; input redirects stay free this milestone —
  document in the task report).
- Integration tests (tests/integration.rs): profile blocking external
  (`--profile` read-only + `false`-style external → not-allowed message,
  status 1), allow-listed external runs, write redirect blocked +
  allowed, cmdsubst inner command blocked, builtin echo runs free in
  read-only, cd runs free in read-only.
- Commit: `profiles: spawn and write gates`

### Task 3: profile files end-to-end + parity

- Wire `load_profile` at all entry points (main.rs script/-c paths already
  from Task 1; verify repl.rs path — the REPL creates its own Runtime:
  pass the profile name through `run_repl` or a global; choose the least-
  invasive: `run_repl(profile: Option<String>)` signature change).
- End-to-end integration tests: profile file with `profile allow echo`
  … wait — echo is a builtin; use a real external (e.g. `sh -c` on Unix /
  `cmd /c` on Windows; tests use cfg to pick). Profile file allowing one
  external + allow-write on a temp dir → external runs, write inside temp
  dir ok, write outside blocked, other external blocked.
- Read-only mode end-to-end: `--profile` alone → every external blocked,
  builtins free, redirect writes blocked.
- Missing profile file: `--profile ghost` → startup error exit 2.
- README.md Status: profiles section (one paragraph: what they are,
  `--profile NAME`, read-only mode, fail-closed semantics).
- Commit: `profiles: end-to-end loading, read-only mode, readme`

### Task 4: Windows smoke + docs

- Cross-compile, copy to fush-smoke, batch-file smoke:

  - `fush.exe --profile -c "echo hi"` → hi (builtin free)

## Review Focus

- Fail-closed everywhere: empty allow-list blocks; missing file errors;
  unknown builtin arg errors; read-only mode cannot be escaped via cmdsubst
  or functions calling externals
- Gates cover ALL spawn paths (pipeline stages, not just first; the
  external arm is the only spawner — verify no other `Command::new`/
  spawn site bypasses it)
- Write gate covers both external redirects and builtin redirect output
- Component-wise prefix match cannot be tricked (`C:\work-evil` is not
  under `C:\work`)
- `--profile` parsing does not eat script paths (`fush --profile dev
  script.fush` = profile dev + script)
